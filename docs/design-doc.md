## 1. 概要

PMMT（部門長MT）の進捗の事前記入と非同期の議論を、Notion から専用の Web アプリに移す。
目指すのは、**決まった締切までに参加者全員（部門長・局長・副局長）が書き、お互いに読んで反応し、確認事項が当日までに片付くか議題にまとまる** という週のサイクルを、仕組みで回すこと。
あわせて、決まったこと・TODO・持ち越した議題を 1 件ずつ記録として残して、あとから検索・振り返りができるようにする。

## 2. 背景

- PMMT は毎週月曜 20:00〜22:00 に対面で行う。参加者は部門長 8 人（チーム 4・プロジェクト 4）と局長・副局長の計 10 人
- 進捗報告は 10 人全員が行う。局長は **実行委員の視点**、副局長は **情報局の視点** で報告・確認をする
- 進捗報告を 1 人 3 分に制限した結果、報告は 30 分に収まった（まだ 1 回だけ）
- 事前記入（Notion）を始めたが、前日までに書くのは約 2 割で毎回同じ人。コメントはほぼゼロで、非同期に回した話が議論されないまま終わっている
- 決まったことや TODO は議事録の中に埋もれていて、見落とすと次回やり忘れる。過去の決定や先送りした議題を Notion から探すのはとても大変
- 45th の振り返りでは「何のためにやっているかわからない」「新入生にはわからない」という声が多かった
- Notion はフリープランのゲストワークスペースで API が実質使えないため、Notion の上に機能を足す方法はとれない

詳細は局内向けのヒアリング資料（非公開）。

## 3. 解く課題

| # | 課題 | 優先度 |
|---|---|---|
| P1 | 非同期が回っていない（締切がない・記入状況が見えない・反応がない・議論が閉じない） | ★★★ |
| P2 | 決まったこと・TODO・先送りした議題が追いかけられない | ★★★ |
| P3 | 記録が回ごとのページにバラバラで、検索・振り返り・AI での参照ができない | ★★ |
| P4 | プロジェクトの目的・状況が伝わらず、あとから調べる場所もない | ★★ |
| P5 | 議事録が読まれず、作る・チェックするのが大変 | ★★ |

## 4. Goals / Non-goals

### Goals（MVP）

- **G1** 参加者全員（部門長・局長・副局長）がスマホでも 5 分で事前記入できる。締切までの記入状況が一目でわかり、Slack でリマインドが届く
- **G2** 「確認すること」に返信・リアクションができ、それぞれを **決定 / 当日に話す / 解決済み** のどれかで閉じられる。「当日に話す」になったものは、そのまま PMMT の議題一覧に並ぶ
- **G3** 決まったこと・TODO・先送りした議題が 1 件ずつ記録として残り、検索できる。終わっていない TODO は次回に自動で持ち越される。46th の過去の PMMT（約 6 回分）の記録も取り込む
- **G4** 全員（全ユニット）の状態（進み具合・忙しさ・他局に関わるか）を 1 画面で見渡せる
- **G5** ユニットごとに目的・概要のページがあり、週ごとの更新がそこに積み重なる
- **G6** 議事録づくり用のスキル（プロンプト）を配る。出力はアプリに取り込める形にそろえる

### Non-goals（MVP ではやらない）

- 進捗とは別の議題（企画の相談・局運営の提案など）の管理
- 局定例MT（約 60 人）での運用と Figjam の置き換え
- 他局への提供、NUTMEG 公式サイトとの連携
- アプリの中から LLM の API を呼ぶこと
- Slack の議論の自動取り込み（MVP では貼り付けで取り込む）
- 進捗の % 表示やチャート

## 6. 週のサイクル（運用設計）

参考：Atlassian の「書く日・読む日を固定する」、Fellow の「TODO を自動で持ち越す」（[既存ツール調査 §4](existing-tools-research.md#4-横断して見えた設計パターン)）

| タイミング | 起きること | アプリの動き |
|---|---|---|
| 月 22:00（PMMT 後） | 次の回が開く | 新しい回を作る。終わっていない TODO と「当日に話す」の残りを持ち越す |
| 火〜木 | 参加者全員が記入 | 水曜夜・木曜夜に、未記入の人へ Slack でリマインド |
| **金 12:00** | **締切** | 締切時点の記入状況を Slack に投稿 |
| 金 午後 | 最強二枚看板の打ち合わせ | 局長・副局長が全員の記入と確認事項を読み、返信・判断する |
| 土〜月 | 非同期の議論 | 返信がつくと、書いた人に通知。各確認事項を 決定 / 当日に話す / 解決済み で閉じる |
| 月 20:00 | PMMT | 「当日に話す」一覧を議題として使う。報告は 1 人 3 分 |
| 月 PMMT 後 | 議事録 | スキルで議事録を作る → アプリに貼り付け → 決まったこと・TODO を 1 件ずつ確認して登録 |

締切とリマインドの時刻は回ごとに変えられる（二枚看板の日程が変わるため）。

## 7. 機能

### 7-1. 優先度

| # | 機能 | 対応する Goal | プロトタイプ |
|---|---|---|---|
| F1 | 回（PMMT 1 回分）の作成・締切設定 | G1 | ✅ |
| F2 | 事前記入フォーム（スマホ対応） | G1 | ✅ |
| F3 | 記入状況ボード | G1 | ✅ |
| F4 | 確認事項のスレッド・リアクション・閉じる操作 | G2 | ✅ |
| F5 | 記録（決まったこと・TODO・先送りした議題）の一覧・検索・持ち越し | G3 | ✅ |
| F6 | 全ユニットのダッシュボード | G4 | ✅ |
| F7 | ユニットの目的・概要ページ | G5 | ✅（シンプルに） |
| F8 | Slack 通知（リマインド・締切・返信） | G1, G2 | ⚪ 締切の投稿だけ |
| F9 | 議事録の取り込み（貼り付け → 1 件ずつ確認して登録） | G3, G6 | ⚪ |
| F10 | 議事録スキルの配布 | G6 | ✅（ファイルを用意するだけ） |
| F11 | 過去の PMMT（46th の約 6 回分）の取り込み | G3 | ⚪ F9 と同じ取り込み口を使う（§7-6） |

✅ = プロトタイプに入れる / ⚪ = 時間があれば

### 7-2. 事前記入フォーム（テンプレートの作り直し）

今の「確認すること / 報告すること / 話したいこと」を、**目的から逆算して** 次の形にする。

| 欄 | 入力 | ねらい |
|---|---|---|
| 進み具合 | 🟢 順調 / 🟡 注意 / 🔴 困っている（チーム・局長・副局長は選ばなくてもいい） | 局長が読む部門を選べる（Linear の Health） |
| 忙しさ | 1〜3 の 3 段階 | 局長が知りたいこと（Q3）。Range の気分共有を参考 |
| 今週やったこと | 箇条書き 1〜3 行 | 報告の中身。当日は話さない |
| 次にやること | 箇条書き 1〜3 行 | 次回の確認に使う |
| 確認したいこと | 1 件ずつ追加。**「他局・実行委員に関わる」チェック** をつけられる | スレッドの単位。局長が他局関連を拾える |
| 話したいこと | 1 件ずつ追加（任意） | 小話やアイデア。リアクションで軽く反応できる |

「確認したいこと」と「話したいこと」は、ページの中の文章ではなく **1 件ずつのアイテム** として持つ。そうすることで、返信・閉じる・記録にする、といった操作ができる。

### 7-3. 確認事項の閉じ方

```
未解決 ──返信・リアクション──▶ 未解決
   │
   ├─▶ 決定      … 決まった内容を一言で書く → 「決まったこと」の記録が自動でできる
   ├─▶ 当日に話す … PMMT の議題一覧に並ぶ。PMMT 後に 決定 / 先送り のどちらかにする
   └─▶ 解決済み  … 返信で片付いたもの
```

- 閉じる操作ができるのは、書いた本人・局長・副局長
- 締切の時点で未解決のものは、ダッシュボードで目立たせる

### 7-4. 記録（決まったこと・TODO・先送りした議題）

- 1 件 = 1 レコード。どの回・どのユニット・どのスレッドから生まれたかの情報を持つ
- 検索は、キーワード・ユニット・種類・期間で絞り込む（Q4：「あの時どう決めた？」「先送りした議題はどれ？」）
- 終わっていない TODO と先送りした議題は、次の回の記入フォームとダッシュボードに出てくる
- 一覧は Markdown で書き出せるようにする（NUTMEG 便りや AI に渡す材料にするため）

### 7-5. 議事録スキルと取り込み

- スキルの出力形式は、見出しを固定した Markdown にする（`## 決まったこと` / `## TODO`（担当ユニット・期限つき） / `## 先送りした議題` / `## 要約`）
- アプリに貼り付けると 1 件ずつの候補になり、局長か副局長が ✓ をつけたものだけ登録される。こうすると、議事録全体を読み返さずに 1 件ずつ確認するだけで済む
- Claude/Codex 向けのスキルと、Claude/ChatGPT/Gemini などAIチャット向けのプロンプトの 2 種類を用意する

### 7-6. 過去の PMMT の取り込み

46th の PMMT はまだ約 6 回分なので、過去の記録も取り込んで、最初から検索できる状態にする。

1. Notion の各回の PMMT ページを Markdown で書き出す
2. 文字起こし・録音がある回は、それも一緒に AI に渡す（Notion ページだけより精度が上がる）
3. 議事録スキルと同じ形式（§7-5）に変換する。見出しに「どの回か（日付）」を加える
4. F9 の取り込み画面に、回の日付を指定して貼り付け → 1 件ずつ確認して登録

取り込みの仕組みを F9 と共通にするので、追加で作るのは「過去の日付で回を作る」機能だけで済む。

## 8. 技術構成

### 8-1. プロトタイプ

| 項目 | 採用 | 理由・メモ |
|---|---|---|
| フレームワーク | **Void**（Vite ベース、Cloudflare Workers 向けフルスタック FW）+ React | ファイルベースのルーティングとサーバー側の loader / action があり、`void deploy` だけで DB の用意からデプロイまで終わる |
| DB | Cloudflare D1（SQLite）+ Drizzle | Void 標準。スキーマは Drizzle で書く |
| 認証 | Void の認証機能（中身は **Better Auth**）+ Google ログイン | ログイン後、アプリの中でメールアドレスをパターン判定する（§9） |
| ホスティング | Cloudflare（`nutmeg.cloud` のサブドメイン） | 無料枠に収まる見込み |
| Slack 通知 | Incoming Webhook で PMMT 用のチャンネルに投稿 | メンションには、メンバーごとに Slack のユーザー ID を登録しておく |
| 定期実行（リマインド・締切） | Void の `crons/`（`defineScheduled`。中身は Cloudflare の Cron Triggers） | 開発中は自動では動かないので、Void が用意している URL を叩いて試す |

### 8-2. 本番に向けて

本番は「他の人が開発しやすい React 系 FW」で「Docker を使ってオンプレ」にする方針。
ただし **Void は Cloudflare 専用**（セルフホスト版も Cloudflare のアカウント上で動くもので、自前のサーバーでは動かない）。なので、**プロトタイプのコードをそのままオンプレに持っていくことはできない**。本番では FW を作り直す前提で、次のものは引き継げるようにしておく。

| 引き継ぐもの | 方法 |
|---|---|
| DB スキーマ | Drizzle で書く。本番も Drizzle を使えば、SQLite のまま行くか PostgreSQL に移るかを選べる |
| 認証 | Better Auth は Void の外でも使えるライブラリ。本番でもそのまま使える |
| ビジネスロジック | 「閉じる」「持ち越す」「議事録の解析」などは、FW に依存しない関数として別ファイルにまとめる |
| UI コンポーネント | React のまま持っていける |

本番の FW 候補：React Router v7（旧 Remix。loader / action の考え方が Void と近いので移しやすい）、TanStack Start、Next.js など。

## 9. 認証・権限

- **プロトタイプ**：Google ログイン（Better Auth）→ アプリの中で `^\d{2}\.[a-z]\.[a-z]+\.nutfes@gmail\.com$` に一致するかを判定する
  - Cloudflare Access ではなくアプリ側で判定する。理由は、Access でパターン指定ができるかわからないことと、無料枠の 50 人の制限を受けないこと
  - ⚠️ 同じ形のアドレスを誰でも作れる、というリスクは承知の上で始める
- **次の段階**：Slack ログイン（招待制のワークスペースのメンバーかどうかで判定）。Better Auth で使えるかは要確認。GitHub の Organization で判定する方法も候補
- **将来**：NUTMEG アカウント基盤
- 判定する部分は 1 つの関数（`resolveMember(user)`）にまとめて、方式を変えても他に影響しないようにする
- 役割は 部門長 / 局長 / 副局長 / 閲覧者（将来）の 4 つ。**管理機能（回・メンバー・報告ユニットの登録、議事録の取り込み）は局長と副局長が使える**

## 10. データモデル（案）

```
Member       id, email, name, role(lead|chief|vice|viewer), unit_id?, slack_user_id?
Unit         id, name, kind(project|team|chief|vice), purpose, summary, sort_order
Cycle        id, meeting_at, deadline_at, status(open|closed)
Report       id, cycle_id, unit_id, author_id,
             progress(green|yellow|red|null), busyness(1-3),
             done_md, next_md, submitted_at?
Item         id, cycle_id, unit_id, author_id,
             kind(confirm|talk), body, cross_bureau(bool),
             state(open|decided|live|resolved), resolution_note?
Comment      id, item_id, author_id, body, created_at
Reaction     id, target(item|comment), target_id, member_id, emoji
Record       id, kind(decision|todo|carryover), title, body,
             unit_id?, cycle_id, source_item_id?,
             assignee_unit_id?, due_cycle_id?, done_at?,
             source(thread|minutes|manual)
```

- 報告ユニット（Unit）= 進捗を報告する単位。部門 8 つに加えて、局長・副局長もそれぞれ 1 つのユニットとして持つ
- 管理機能を使えるかどうかは `role in (chief, vice)` で判定する
- 「記入済み」= その回・そのユニットの `Report.submitted_at` が入っていること
- 局・部門の名前はデータとして持ち、コードに直接書かない（他局に広げる時のため）
- 過去の回を取り込む時のため、`Cycle` は過去の日付でも作れるようにする

## 13. リスクと対策

| リスク | 対策 |
|---|---|
| アプリを作っても記入が遅いまま（原因がツールではない） | プロトタイプ完成後に部門長へミニアンケートを行い、Design Doc を直す（開発フロー 5） |
| 反応する人が局長・副局長だけになる | 他部門の確認事項への反応を、PMMT の冒頭でふり返る運用ルールを検討する |
| 引継ぎ・保守する人がいなくなる | 局運営開発チームの体制で持つ。本番は React 系 FW + Docker で、引き継ぎやすい構成にする |
| プロトタイプから本番への作り直しが重い | §8-2 の方針で、スキーマ・認証・ロジックを引き継げる形にしておく |
| パターン判定の認証の弱さ | §9 の段階的な移行 |

### プロトタイプでの割り切り
- ログインは Google（アドレスの形式チェック + 登録されたメンバーのみ）。ローカル・デモ用に `DEMO_MODE` でメンバーを選んでログインできる
- リアクションは 5 種類の固定（👍 👀 🙏 🎉 ❓）
- 通知は PMMT 用チャンネル 1 つへの投稿のみ（DM はしない）
- テストはロジック（`lib/domain.ts`）の単体テストと、ブラウザでの手動確認のみ
